# Назва проєкту: Агентство нерухомості

**Короткий опис:** модель агентства нерухомості. Клієнти обирають житло за допомогою рієлторів, які, в свою чергу, проводять угоди.

**Опис предметної області:** система вирішує проблему підбору нерухомості. Користувачами системи є люди, які хочуть легко купити/продати житло та рієлтори, у яких буде платформа для заробітку.

**Перелік учасників:** Олексій Гунько, Кирило Колісниченко, Ян Бойко (всі ІПЗ-24-1).

**Основні сценарії використання:**
1. Клієнт обирає об'єкт нерухомості на сайті.
2. Рієлтор розміщує новий об'єкт.
3. Рієлтор проводить угоду.
4. Рієлтор знімає об'єкт із сайту.

**Перелік ресурсів API:**
1. Список об'єктів нерухомості (Properties).
2. Список клієнтів (Clients).
3. Список рієлторів (Agents).
4. Список угод (Deals).

**Перелік реалізованих endpoints:**
* Отримання об'єктів, угод, клієнтів та рієлторів за ID (GET).
* Отримання списків із підтримкою фільтрації (за ціною, кімнатами, статусом тощо) та сортування (GET).
* Зміна характеристик сутностей (PUT).
* Створення нових записів у системі (POST).
* Видалення записів (DELETE).

## База даних та структура моделі

**Використана СУБД:**
У проєкті використовується **SQLite** як легка реляційна база даних для розробки. Взаємодія з БД реалізована через ORM-фреймворк **Entity Framework Core 10.0** за підходом *Code-First* (схема БД генерується на основі коду C#).

**Основні сутності:**
* `Property` (Нерухомість) — зберігає інформацію про об'єкт: адресу, ціну, тип приміщення, кількість кімнат та статус доступності.
* `Client` (Клієнт) — контактні дані клієнта: ПІБ, Email, номер телефону.
* `Agent` (Рієлтор) — робочі дані співробітника: ПІБ, Email, телефон, номер ліцензії, статус активності.
* `Deal` (Угода) — факт укладання договору. Містить дату, кінцеву ціну та поточний статус (наприклад, Pending).

**Зв'язки між сутностями:**
Сутність `Deal` (Угода) виступає центральною таблицею, яка об'єднує інші сутності через відношення **Один-до-багатьох (1:N)**:
* **1** об'єкт `Property` може мати багато угод (наприклад, історія оренди), але **1** конкретна угода стосується лише **1** об'єкта нерухомості (зв'язок через `PropertyId`).
* **1** `Client` може укладати багато угод, але **1** угода належить **1** клієнту (зв'язок через `ClientId`).
* **1** `Agent` (Рієлтор) може проводити багато угод, але за **1** конкретну угоду відповідає **1** рієлтор (зв'язок через `RealtorId`).
Усі зв'язки налаштовані за допомогою зовнішніх ключів (`ForeignKey`) із підтримкою каскадного видалення.

## Архітектура та структура проєкту

Проєкт побудований за принципами **Clean Architecture)** та **SOLID**, із чітким розділенням відповідальності на шари:

1. **Controllers (Контролери):** Відповідають виключно за прийом HTTP-запитів, валідацію вхідних DTO, виклик відповідного сервісу та повернення HTTP-відповідей (200 OK, 404 Not Found, 400 Bad Request тощо). Вони не містять бізнес-логіки.
2. **Services (Сервісний шар):** Ядро системи. Тут зосереджена вся бізнес-логіка. Сервіси отримують дані від контролерів, застосовують бізнес-правила та взаємодіють з базою даних через шар доступу до даних.
3. **Repositories & Unit of Work (Шар доступу до даних):** Ізолює логіку роботи з базою даних. `Repository` відповідає за базові CRUD-операції, а `UnitOfWork` забезпечує виконання кількох операцій як єдиної транзакції (наприклад, збереження клієнта та угоди одночасно).
4. **Models / Entities (Сутності):** Класи, які відображають структуру бази даних (Property, Client, Deal, Agent, ApplicationUser). Використовуються лише на рівні репозиторіїв та сервісів.
5. **DTO (Data Transfer Objects):** Об'єкти передачі даних. Використовуються для обміну даними між клієнтом (Swagger/Postman) та контролерами, що дозволяє приховати внутрішню структуру бази даних і захистити систему від надлишкового передавання даних (Over-posting).

### Принцип Dependency Injection (Впровадження залежностей)

Проєкт активно використовує вбудований DI-контейнер ASP.NET Core для управління життєвими циклами об'єктів. Це дозволяє уникнути жорсткої прив'язки компонентів один до одного, роблячи код гнучким і придатним до модульного тестування (через використання інтерфейсів, наприклад `IPropertyService`).

- **Scoped:** Використовується для репозиторіїв, `UnitOfWork` та сервісів. Екземпляр створюється один раз на кожен HTTP-запит. Це критично важливо для `DbContext`, щоб гарантувати цілісність даних у межах одного запиту.
- **Transient / Singleton:** Застосовується для утиліт, кешування або конфігурацій (наприклад, `HttpClientFactory` для інтеграції з зовнішніми сервісами).

## Безпека: Автентифікація та Авторизація

**Система автентифікації:** 
Безпека API побудована на базі **ASP.NET Core Identity** (для надійного збереження користувачів та хешування паролів) та **JWT (JSON Web Tokens)** для Stateless-автентифікації клієнтів.

**Ролі користувачів:**
У системі передбачено рольову модель доступу (RBAC):
- **User (Користувач / Клієнт):** Базовий рівень доступу. Може переглядати об'єкти нерухомості, редагувати власний профіль та створювати заявки/угоди.
- **Administrator (Адміністратор):** Має повний доступ до системи. Може видаляти об'єкти, керувати обліковими записами рієлторів, змінювати будь-які статуси угод та мати доступ до прихованих endpoints.

### Порядок отримання та використання JWT:
1. **Реєстрація:** Користувач відправляє POST-запит на `api/auth/register` із вказанням Email та пароля.
2. **Логін:** Користувач відправляє POST-запит на `api/auth/login`. Якщо облікові дані правильні, сервер повертає у відповіді JWT-токен.
3. **Авторизація запитів:** Для доступу до захищених ресурсів отриманий токен необхідно додавати до заголовка HTTP-запиту:
   `Authorization: Bearer <ваш_jwt_токен>`

### Приклади захищених endpoint'ів:
- `GET /api/properties` — Доступно для всіх (атрибут `[AllowAnonymous]`).
- `POST /api/deals` — Доступно лише для авторизованих користувачів будь-якої ролі (атрибут `[Authorize]`).
- `DELETE /api/properties/{id}` — Суворо захищений ресурс. Доступний виключно адміністраторам (атрибут `[Authorize(Roles = "Administrator")]`).
- `POST /api/agents` — Реєстрація нових рієлторів доступна лише адміністраторам системи.

## Кешування даних

Для прискорення читання даних, які запитуються часто, але оновлюються рідко, у проєкті налаштовано підсистему кешування на рівні сервісного шару.

### Обраний підхід

Обрано підхід **In-Memory Cache (патерн Cache-Aside)** на базі `Microsoft.Extensions.Caching.Memory.IMemoryCache`, огорнутий у власний сервіс `ICacheService` / `MemoryCacheService`.

Для монолітного сервісу на стадії розробки та навчального проєкту локальний memory cache є оптимальним вибором: він не вимагає розгортання окремого сервера Redis, не створює мережевих затримок і працює безпосередньо в оперативній пам'яті процесу. При цьому інтерфейс `ICacheService` дозволяє за потреби переключити реалізацію на розподілений кеш (`IDistributedCache` або Redis) без змін у коді бізнес-сервісів чи контролерів.

### Відповіді на ключові питання

#### 1. Які дані кешуються?
Кешування застосовано до читання трьох категорій ресурсів:
- **Об'єкти нерухомості (`/api/properties`):** списки з урахуванням усіх комбінацій query-параметрів (ціна, кімнати, тип, доступність, пошук, сортування), а також детальна картка конкретного об'єкта за його id (`/api/properties/{id}`). Каталог житла переглядають часто, а змінюється він переважно рієлторами під час публікації чи редагування.
- **Рієлтори (`/api/agents`):** загальний перелік агентів та сторінка конкретного рієлтора (`/api/agents/{id}`). Штат агентства та контактні дані є найбільш стабільними даними в системі.
- **Курси валют НБУ (`/api/currency/rates` та `/api/currency/rates/{code}`):** відповідь від зовнішнього API Національного банку України. Офіційний курс НБУ оновлюється лише один раз на добу, тому робити запит до зовнішнього сервера на кожен клієнтський перегляд чи конвертацію нераціонально.

Списки клієнтів (`/api/clients`) та угод (`/api/deals`) не кешуються навмисно: це динамічні сутності з чутливими персональними даними, які змінюються часто і мають відображати актуальний стан транзакцій у режимі реального часу.

#### 2. Коли дані додаються до кешу?
Застосовано класичний патерн **Cache-Aside (Lazy Loading)**:
- При надходженні запиту на читання сервіс формує ключ запису (наприклад, `properties:list:{...}` або `properties:details:2`) і перевіряє його наявність у кеші.
- Якщо запис знайдено (**Cache Hit**) — він одразу повертається з пам'яті без звернення до SQLite чи зовнішнього API.
- Якщо запису немає (**Cache Miss**) — дані зчитуються з джерела (база даних або НБУ), зберігаються в кеші для наступних викликів і повертаються клієнту.
- Дані із помилковими статусами (наприклад, 404, якщо об'єкта не існує) у кеш не записуються, щоб не блокувати появу щойно створеного об'єкта з таким самим id.

#### 3. Коли кеш вважається недійсним?
Запис у кеші втрачає актуальність у таких випадках:
- **За часом (Time-To-Live):**
  - Для об'єктів нерухомості та рієлторів діє ковзне вікно (sliding expiration) тривалістю 3 хвилини з абсолютним обмеженням (absolute expiration) у 10 хвилин. Якщо запис не запитують протягом 3 хвилин, він видаляється, але навіть при постійних запитах він не проживе довше 10 хвилин.
  - Для курсів валют НБУ встановлено фіксований абсолютний час життя 60 хвилин, оскільки значення на стороні регулятора протягом дня не змінюються.
- **За витісненням (Size Limit):**
  - У конфігурації задано ліміт на 1000 записів. Якщо пам'ять заповнюється, runtime витісняє найменш використовувані елементи.
- **Явна інвалідація під час мутацій:**
  - Як тільки дані змінюються через POST/PUT/DELETE, пов'язані записи кешу стають недійсними негайно, не чекаючи закінчення таймерів.

#### 4. Як виконується інвалідація кешу?
Для групової інвалідації використано механізм **CancellationChangeToken** ASP.NET Core:
- Записи розподілені за регіонами (`properties`, `agents`, `currency`).
- Кожен регіон пов'язаний із власним `CancellationTokenSource`. Під час збереження елемента в кеш йому передається change token відповідного регіону.
- При будь-якій мутації (створення, редагування, видалення об'єкта або зміна статусу угоди) сервіс викликає `InvalidateRegions(...)`:
  - `POST / PUT / DELETE /api/properties` скидає регіон `properties`.
  - `POST / PUT / DELETE /api/agents` скидає регіон `agents` і пов'язаний з ним регіон `properties` (бо ім'я рієлтора виводиться в деталях угод об'єкта).
  - Створення, зміна статусу або видалення угоди через `DealsController` також скидає регіони `properties` та `agents`, тому що угода перемикає статус доступності об'єкта (`isAvailable`) і змінює історію угод у детальних картках.
  - Редагування клієнта інвалідує об'єкти та агентів через оновлення ПІБ у вкладених списках угод.
- Скасування токена автоматично і миттєво інвалідує всі збережені списки та детальні перегляди цього регіону без необхідності перебирати чи вгадувати окремі ключі запитів.

#### 5. Що відбувається, якщо кеш недоступний?
Архітектура побудована за принципом **Graceful Degradation (відмовостійкість)**:
- Операції читання та запису до кешу всередині `MemoryCacheService` захищені блоками `try/catch` із логуванням попереджень.
- Якщо під час читання кешу виникає будь-який збій (наприклад, пошкодження пам'яті чи нестача ресурсів), метод просто фіксує попередження в логах і прозоро йде за актуальними даними до джерела (бази даних SQLite або НБУ API).
- Якщо кешування повністю вимкнути через налаштування `"Caching:Enabled": false` у файлі `appsettings.json`, сервіс одразу перенаправляє всі запити до бази даних чи зовнішнього API, не перериваючи роботу застосунку.

### Налаштування параметрів кешування

Керування поведінкою кешу винесено у файл `appsettings.json`:

```json
"Caching": {
  "Enabled": true,
  "SizeLimit": 1000,
  "EntityAbsoluteExpirationMinutes": 10,
  "EntitySlidingExpirationMinutes": 3,
  "CurrencyRatesExpirationMinutes": 60
}
```

## Інструкція із запуску та налаштування бази даних

**Налаштування підключення:**
Рядок підключення до бази даних зберігається у файлі `appsettings.json`:
"ConnectionStrings": {
  "DefaultConnection": "Data Source=realestate.db"
}
Файл фізичної бази даних (realestate.db) генерується автоматично у кореневій папці проєкту під час першого застосування міграцій.

**Порядок застосування міграцій:**
Для ініціалізації бази даних на новому комп'ютері або після оновлення моделей необхідно застосувати міграції EF Core.
Відкрийте термінал у кореневій папці проєкту та виконайте наступні кроки:

Для створення/оновлення бази даних до актуального стану (накатування наявних міграцій):
dotnet ef database update
(Опціонально) Якщо ви внесли зміни в класи моделей (наприклад, додали нове поле) і хочете зафіксувати їх:
dotnet ef migrations add <НазваВашоїМіграції>
Після успішного створення міграції знову виконайте dotnet ef database update.

**Запуск проєкту:**

Запустіть проєкт у Visual Studio за допомогою F5 або виконайте команду dotnet run у терміналі.

Введіть в адресному рядку браузера http://localhost:[порт]/swagger (порт можна знайти у файлі Properties/launchSettings.json або у виводі терміналу).

Через інтерфейс Swagger UI ви можете ознайомитися з документацією API та протестувати всі реалізовані REST-операції.

Щоб тестувати захищені endpoints, натисніть кнопку Authorize (іконка замка) у Swagger і введіть JWT токен у форматі Bearer <token>.
